## Current Technical Shape

The functional baseline (connect-negotiate, authentication, invoke, send, server-stream, callbacks, concurrency-and-clones, large-payload, server-close, reconnect-exhaustion) and the TLS, negotiation, liveness and lifecycle scenarios run natively from `tests/e2e` (also on the Android emulator and iOS simulator) and in Chromium, Firefox and WebKit from the fixture's `run_functional_scenario` (`tests/wasm-fixture/src/functional.rs`, `signalr-*.spec.ts`), JSON and MessagePack. On Android the TLS scenario verifies the untrusted case with bundled roots, because the platform verifier needs an app's JVM. The `error-kinds` scenario (every native and browser target; `Tls` natively only) asserts the typed error kind and fields of a throwing hub method, rejected credentials (401), an unknown hub (404), a never-answered negotiate under a 2 s connect timeout, an undecodable result, invoking while paused, a server close with its message, invoking through a clone after `disconnect` (`ConnectionClosed`/`Local`) and an untrusted certificate, and that no error repeats the test token; `disconnect-every-handle` proves `StopAsync` parity (a clone's pending invocation and open stream end at once, a registered callback does not keep the connection open, every handle reports `Closed`, the hub sees one disconnect) and `concurrency-and-clones` that dropping a clone keeps the connection; scenarios and unit tests assert kinds and structured fields, keeping message text only where it is the property (redaction, endpoint naming, server text). The P2 lifecycle scenarios (every target, both protocols): `connected-callback`, `restart-after-stop`, `lifecycle-events`, `connection-id`, `graceful-stop` (asserts the hub counted the Close message) and `reconnect-call-wait` (calls during a held reconnect attempt). Unit tests that need a successful connection use the `#[cfg(test)]` loopback SignalR server `src/communication/loopback_server.rs` (negotiate, JSON handshake with optional delay and greeting, records, dropped or stalled connections, delayed 503 rejections, recorded negotiate/upgrade request heads, an optional `useStatefulReconnect` offer; dev-dependency `tokio-websockets` `server` feature). The P3 wire-parity unit groups (`wire_parity` modules in `client.rs` and `client_tokio.rs`, plus module tests) are `request_headers_`, `protocol_violation_`, `framing_carryover_`, `invocation_headers_`, `case_insensitive_payload_`, `stateful_ack_cadence_`, `token_placement_`, `negotiate_parity_` and `server_text_`; the `request-headers` scenario runs on every target. P4 added the `stateful_transparent_` group (buffer `Held` frames, loopback resume without policy/events, failed resume through the policy or to `Closed`, server Close, client-result reply and waiting send across a resume, a waiting send never moving to a new logical connection, pause cancelling a resume; the loopback server recognizes a resume by its token and has `resume_delay`, `reject_resumes`, `resumes()`, `try_next_record`) and the `stateful-transparent-resume` and `stateful-resume-fallback` scenarios (every target); `connection-id` waits for `TransportAbortCount` instead of `Reconnected` after a stateful drop. S4 added the long cells (native, Chromium, Android; Firefox/WebKit/iOS are documented catalog exclusions and the Firefox/WebKit Playwright projects ignore their specs): `soak-chaos` (`tests/e2e/soak_chaos.rs`, `tests/wasm-fixture/src/soak.rs`, `signalr-soak.spec.ts`) runs an ordinary and a stateful client concurrently for `RAYX_SIGNALR_SOAK_SECONDS` (default 120; `Scenario.Soak`, bound soak + 60 s) under random 0.5-5 s chaos, natively on a dedicated runtime whose `num_alive_tasks()` must return to its pre-connect value; `stateful-resume-stress` (`stateful_resume_stress.rs`, `stress.rs`, `signalr-stress.spec.ts`; `Limit` 600 s, `LogFilter` adds `rayx_signalr::stateful=debug`; the browser keeps a 400-record trace ring) does 5 x 100 aborts. `support::bounded_within`/`soak_duration` serve them; `LongCellTests` (Catalog) proves the bounds and the forwarding. S5 added the groups `access_token_factory_` (11, incl. a loopback `redirect_token` option), `browser_basic_` and `connect_timeout_`, and the `token-factory` and `negotiate-timeout` scenarios (every target; the factory fetches tokens through a probe client). Unit group `error_model_` covers the error type and argument-encode failures, `disconnect_` the every-handle close and the last-handle drop; `tests/public_error_types.rs` asserts the public fallible signatures. Black-box native scenarios in `tests/e2e` (`test = false`; public API only; transports dropped through the hub's `AbortPhysicalTransport`) cover ordinary reconnect, stateful reconnect (aborts during a stream and during a pending invocation, verified by `TransportAbortCount`), and 64-round dropped-stream cancellation in JSON and MessagePack. The WASM fixture remains a `wasm_bindgen(start)` browser program, but Playwright 1.59.1 drives it in real Chromium, Firefox and WebKit with the same reconnect/cancellation matrix plus short stream chaining. Cancellation cells require zero active server enumerators, one observed server cancellation and one type-5 wire frame per drop, a still-usable connection, and no page errors; natural completion requires zero cancellation frames. Protocol and buffer unit tests cover exact JSON/MessagePack CancelInvocation shapes, Ack/Sequence golden frames, bounded replay, backpressure, duplicate suppression, gaps, overflow, disposal, and cumulative acknowledgements; the `sequence_trace_` group asserts the payload-free stateful sequencing records (including wire-level rejections) through a thread-scoped capturing logger (`src/test_logging.rs`, the only logger unit tests may install). Measurement: `benches/hot_paths.rs` runs Criterion over the internal codec and action storage through the hidden `bench_support` module (unstable `bench-internals` feature, stable ids `hot_paths/<inbound|outbound|framing>/<protocol>/<message>/<size>`; Criterion stores them with slashes turned into underscores under `target/criterion`), and the Aspire `Performance` category runs the release `tests/perf` binary (`test = false`, so Clippy and checks must name `--test perf`) and the official .NET client (`dotnet/RayX.SignalR.PerfReference`) on identical, identically warmed-up workloads (`invoke-latency`, `stream-throughput`, `send-throughput`, `fan-in`; 2 s warm-up at `full`, a tenth at `quick`) in three interleaved rounds, records the medians with warm-up size, build profile and machine in `artifacts-temp/perf/<run>.json`, and runs only when `RAYX_SIGNALR_PERF_WORKLOADS` selects workloads. Only warmed-up comparisons are meaningful: a cold .NET reference understates it several-fold.
